# Java 后端开发规范手册

## 1. 目的与适用范围

本手册用于 Java 后端项目的新功能开发、存量重构和代码评审。内容覆盖模块边界、数据所有权、Java 类和方法规范、SQL 与迁移、真实数据库测试，以及存储、AI 和诊断能力。

手册只规定通用工程原则。具体项目应另行确定技术栈版本、接口契约、错误码、数据库类型、迁移工具、部署拓扑和安全等级；这些项目决定不能被本手册中的示例替代。

规范中的“必须”是准入要求，“应”是默认做法，“可以”表示在有明确理由时使用。任何例外都要写出原因、影响和验证方式。

每条规范只表达一个可判断的要求。条款按“要求、适用范围、理由、示例或反例”组织；示例只用于解释规则，不构成额外契约。涉及 Java、数据库或框架版本的条款必须注明适用范围，不能把某一历史版本的实现细节当作普遍标准。

## 2. 模块边界与数据所有权

### 2.1 模块划分

业务模块按领域职责划分，基础模块只提供跨领域基础能力，应用模块负责启动和装配。一个模块应能用一句话说明自己的业务责任和数据边界。

常见分层如下：

| 层次 | 责任 |
|---|---|
| 基础设施层 | 配置、日志、异常、缓存、数据库和通用客户端 |
| 接入层 | HTTP、RPC、消息订阅、认证和协议适配 |
| 业务模块 | 一个明确领域内的用例、状态和持久化 |
| 应用装配层 | 启动、模块组合和环境配置 |

基础设施层不得反向依赖业务模块。业务模块之间的依赖必须有明确用例，不能因为“方便复用”直接共享内部实现。

### 2.2 数据所有权

每张业务表必须指定一个负责模块。所有权包括写入、状态转换、约束解释、迁移和数据修复责任，不只是 Entity 或 Mapper 所在的 Java 包。

其他模块访问数据时遵守以下规则：

1. 不直接注入其他模块的 Mapper、Repository 或 DAO。
2. 不在自己的 SQL/XML 中读取或修改其他模块的业务表。
3. 通过最小化的查询接口、命令接口或领域事件获取数据。
4. 跨模块接口使用专用 Request/Response 或不可变值对象，不暴露 Entity、ORM 条件对象和供应商 SDK 类型。
5. 跨模块只读聚合必须明确查询所有者、权限条件、排序方式和性能依据，不能为了形式上的分层造成 N+1 查询。

### 2.3 同步调用与事件

调用方必须立即得到业务结果时使用同步接口；事实已经发生、消费者可以独立处理时使用事件。事件设计必须说明：

- 发布时点，是事务提交前还是提交后；
- 重复消费如何去重；
- 消费失败如何重试、告警和恢复；
- 事件载荷是事实快照还是只包含资源 ID。

不能用事件隐藏必须同步返回的校验结果，也不能把进程内事件当作可靠消息投递。

### 2.4 防止过度分层

新增 Facade、Manager、Assembler、Repository 或 API 子模块前，必须说明它与现有层的不同职责。仅转发且没有隔离、适配或权限职责的包装类不应新增；具有稳定边界价值的适配器不受转调次数限制。共享代码只有在多个模块拥有稳定、相同语义时才进入公共模块。

## 3. Java 类和代码规范

### 3.1 类职责

评审者只读类声明和主入口，就应能回答：类负责什么、不负责什么；调用前提是什么；主流程有哪些步骤；读写哪些数据；失败如何返回；重复调用是否安全。无法回答时，优先调整职责和命名，不靠增加注释掩盖复杂度。

### 3.2 分层职责

| 类型 | 允许做什么 | 禁止做什么 |
|---|---|---|
| Controller | 路由、参数绑定、校验、调用 Service、返回统一响应 | 业务分支、事务控制、直接访问 Mapper、拼装业务 Map |
| Service | 用例流程、权限和状态校验、事务边界、幂等处理 | HTTP 报文细节、SQL 字符串、供应商协议解析 |
| Mapper/Repository | 查询、更新、映射、影响行数和持久化条件 | 远程调用、业务编排、隐藏权限条件 |
| Entity | 持久化映射及必要的不变量 | 请求上下文、响应装配、虚构字段 |
| Request/Response | 一个动作的输入或输出 | Entity、内部状态机、服务端内部字段 |
| Client | 外部协议、超时、重试边界和错误转换 | 直接决定业务权益或写业务表 |
| Listener | 校验事件并委托用例 | 承载完整业务流程、吞掉异常 |

Controller 应保持简短，但不以固定行数判定合格；协议解析可以有分支，业务决策仍交给 Service。Service 主方法应保持同一抽象层级，避免把 HTTP、SQL、JSON、远程调用和业务判断混在一起。

### 3.3 文件结构与依赖

类文件按以下顺序组织：包声明、显式 import、类级 Javadoc、注解、类声明、常量、依赖字段、构造器、公开方法、辅助方法。辅助方法按主流程阅读顺序排列。

必需依赖使用构造器注入和 `private final` 字段。依赖注入组件应有明确的注入构造器；值对象和框架管理的实体可按不变量及框架要求提供其他构造器。必要依赖缺失时应在启动或调用边界明确失败，禁止通过 `null`、可选注入或空操作伪造成功。

复用框架管理的序列化器、HTTP 客户端和配置对象，不在方法内临时创建行为不同的实例。新增代码使用统一 formatter；未确定 formatter 前，不在功能提交中批量重排存量代码。

### 3.4 命名

- 包名全小写；类名 UpperCamelCase，表达对象和职责，例如 `OrderService`、`ObjectStorageClient`。
- 方法名使用动词加对象，例如 `createOrder`、`findActiveSubscription`。
- `find` 表示允许不存在；`getRequired` 表示不存在即抛异常；`list` 返回集合；`page` 表示数据库分页。
- `is`、`has`、`can` 只用于布尔判断；`validate` 必须明确失败时是否抛异常。
- 变量名表达业务角色和单位，例如 `ownedResourceIds`、`retryDelaySeconds`。禁止用 `data`、`obj`、`temp`、`flag` 掩盖语义。
- 常量使用 `UPPER_SNAKE_CASE`，名称必须表达规则含义。方法、参数和变量使用 lowerCamelCase；数组声明采用 `String[] names`，long 字面量采用大写 `L`。
- 抽象类应以 Abstract 开头，异常以 Exception 结尾，测试类以 Test 结尾。禁止拼音混拼和无意义缩写；循环索引 i、j 和泛型 T 可以使用。
- JavaBeans 布尔字段应区分字段名与 is/get 访问器；针对布尔类型（如 isNewUser、isRead），必须显式声明 @JsonProperty("isXxx")，阻断 Jackson 反向解析时将属性名吞为 newUser 或 read 引发的字段丢失；JSON 名称不一致时显式映射并测试。全库严格禁止使用 Java record。
- DTO 使用稳定的 `Request`、`Response`、`Query` 等后缀。DTO、VO、BO、Command 可以共存，但必须说明各自边界；不得为相同职责重复建立模型层。
- 测试方法使用行为名称，例如 `shouldRejectUpdateWhenResourceIsNotOwned`。
- 禁止用 `New`、`Temp`、`Impl2` 或无语义的 `V2` 掩盖职责；版本后缀只能表示已确认的契约版本。

### 3.5 方法编排与复杂度

业务方法通常按以下顺序组织：确认输入和身份、读取数据、校验归属和状态、计算结果、持久化、执行已批准的副作用。特殊顺序必须有业务理由。

异常路径尽早返回或抛出，成功路径保持连续。方法超过约 40 个非空非注释行，或控制流超过三层时，必须进行职责审查。该阈值是审查信号，不要求机械拆出空转类。

抽取方法必须对应可命名的业务步骤或独立算法。禁止 `step1`、`processInternal2` 等无语义拆分。带副作用的流程使用普通循环；Stream 只用于简单转换和筛选，不能把写库或远程调用放进 `map`、`peek`。

### 3.6 类型、DTO 与注释

- 时间点使用明确的时间类型，日历日期与时间点不能混用；时区转换在边界显式完成。
- 集合查询返回空集合；单对象不存在的行为由方法名和契约决定。
- 未知值不能用空字符串、零值或虚构对象替代。
- 全库模型类与 DTO 严格禁止使用 Java record 类型，统一采用纯净标准的 POJO JavaBean（标准私有字段、显式 Getter/Setter、无参构造器、全参构造器，以及标准的 equals/hashCode/toString 方法），确保极致的代码可读性与序列化兼容性；禁止用 `Map<String, Object>` 逃避契约设计。
- 采用表映射模式的 Entity 与物理表结构 1:1 映射；全库统一使用 MyBatis-Plus 内置原生雪花算法 (`IdType.ASSIGN_ID`)，采用标准 `String` 或 `Long` 类型；严禁在业务实体中使用 `byte[]` 存储密文或盲索引；不要把请求字段、缓存字段和响应计算字段塞进 Entity。
- 类、接口和枚举必须有类级 Javadoc；核心对外方法说明输入前提、空值、返回、异常和副作用；Service 多步业务流强制标注 `// 1. ...`、`// 2. ...` 编号步骤注释。
- 步骤注释描述业务目的，例如“验证资源归属”，不要描述语法动作，例如“执行 if 判断”。

### 3.7 异常、日志与安全

统一使用项目规定的异常、错误码和响应模型（`Result<T>`、`BusinessException`、`ErrorCode`）。输入非法、未认证、无权限、不存在、状态冲突和外部失败必须有可区分的语义，不能用空成功或泛化 500 掩盖错误。

只在能增加上下文、转换错误或执行明确恢复的边界捕获异常。捕获后不能只打印日志继续执行。日志不得包含 Token、密钥、完整请求体、敏感字段、私有 URL 或完整供应商响应。

身份必须来自服务端单点上下文事实源 `UserContext.getUserId()`。受用户或租户范围约束的单条、批量、分页、更新和删除操作必须校验授权范围；公共数据和系统任务使用明确的访问策略。`UserContext` 上下文、MDC 和线程变量必须在请求或异步任务结束时清理（`afterCompletion` 中强制 `UserContext.clear()`），彻底防串号。严禁在 Service 中声明 `ConcurrentHashMap` 等本地内存结构充当“Redis 故障兜底”。

### 3.8 事务、异步与幂等

事务边界放在 Service 用例入口。状态更新必须带上资源、归属和期望旧状态等条件，并检查影响行数。零行结果要区分已完成、不存在、无权限和状态冲突。

外部 HTTP、模型、支付和对象存储调用应有明确的事务外边界。使用 Spring 代理模式时，事务注解、异步注解和同类方法调用必须验证是否经过代理 [S5]，不能以注解存在推断运行时生效。

异步任务使用不可变 ID 或快照，明确快照时点、线程池容量、拒绝策略、失败归属和重试上限。重复请求和重复消费必须满足幂等要求。

### 3.9 格式与控制语句

1. 使用统一格式化工具；缩进、行宽、换行符和字符集由项目 formatter 统一决定。格式化规则不得在单次功能提交中与业务修改混杂变更。
2. 条件、循环和 `switch` 使用大括号。`switch` 必须明确每个分支的终止或贯穿意图，并保证分支完整；现代 Java 的穷尽式 switch 表达式不强制增加冗余 default。
3. 复杂条件先赋予有业务含义的布尔变量，异常路径优先使用卫语句。控制流超过三层或单方法超过约 40 个非空非注释行时，必须进行职责审查；阈值是审查信号，不是机械拆分类的命令。

### 3.10 类型、集合与对象契约

1. 覆写方法必须使用 `@Override`。外部已使用的接口变更必须通过兼容扩展、版本化或弃用迁移完成，不能直接改写原方法语义。
2. 包装类型与基本类型按可空性选择：外部输入、持久化字段和远程契约需要表达“未知”时使用包装类型；局部计算使用基本类型时必须先完成空值处理。
3. 对象值比较使用 `equals` 或 `Objects.equals`，不得用 `==` 比较包装类型。重写 `equals` 时必须同时遵守 `hashCode` 契约。
4. 集合返回值的空结果、未知结果和失败结果必须有清晰区分。集合视图、不可变集合和可修改集合的行为必须在接口契约中说明。
5. 不在增强 `for` 循环中直接修改正在遍历的集合；需要删除时使用迭代器或构造新集合。使用 `subList`、`Arrays.asList` 和 `toArray` 时必须遵守其视图和可变性约束。
6. 泛型需要表达协变或逆变边界时遵守 PECS：生产数据使用 `? extends T`，消费数据使用 `? super T`；不得为逃避类型设计使用原始类型或 `Object`；`? super T` 可以读取，但静态读取类型通常是 Object。
7. 比较器必须满足反对称、传递和一致性约束，并为相等值返回零。排序结果需要稳定时，必须提供确定的第二排序键。
8. 集合容量可以根据已知规模预设；无法估算时优先保证正确性，不以未经测量的容量计算作为硬性性能承诺。

### 3.11 并发与资源

1. 线程、线程池和定时任务必须有明确的生命周期管理者，线程名称应能定位所属用途；禁止在业务方法内随意创建未受控线程。
2. 平台线程池必须明确核心线程数、最大线程数、队列容量、拒绝策略、关闭策略和任务超时。不得使用无界队列或线程创建掩盖容量决策。Java 21 虚拟线程按任务创建，不应池化；使用信号量或入口限流控制数据库和外部服务的并发量。[S2]
3. 锁只保护必要的共享状态，锁内应避免阻塞 I/O；必须执行时需评估超时和锁持有时间。多个资源加锁时必须约定一致顺序，避免死锁。
4. `volatile` 只解决可见性，不保证复合操作的原子性。计数、状态转换和并发更新应使用原子类、数据库条件更新或明确的锁策略。
5. 共享的 `ThreadLocal`、MDC、请求上下文和安全上下文必须在任务结束时清理；线程池复用场景尤其需要验证异常路径清理。
6. 并发更新必须选择乐观锁、悲观锁、唯一约束或幂等键中的适当机制，并通过冲突测试证明不会丢失更新。

### 3.12 异常、日志与注释细则

1. 不用异常代替正常分支，不捕获后空处理，也不捕获 `Exception` 后伪造成功。异常必须保留原始原因，并在边界转换为调用方可理解的错误语义。
2. 资源使用优先采用 `try-with-resources`。禁止在 `finally` 中使用 `return`；关闭资源的异常必须按项目策略记录或合并。
3. 日志使用统一门面和参数占位符，不通过字符串拼接构造低级别日志。异常日志同时包含现场上下文和堆栈，但不得记录凭证、密钥、完整敏感请求或未脱敏个人数据。
4. 日志只记录能支持排障或审计的事实；重复打印同一异常、无边界的循环日志和生产环境调试日志必须受控。
5. 类、接口、枚举、公共方法和抽象方法的 Javadoc 应说明职责、输入前提、返回值、异常和副作用。成员字段和枚举项在其含义不直观时补充说明。
6. 注释必须随代码同步更新。废弃代码直接删除；保留 TODO 或 FIXME 时必须写明责任人、时间和处理条件，不能把注释当作长期任务系统。

### 3.13 常量、构造器与访问控制

1. 业务规则中的固定值必须命名，禁止魔法数字、魔法字符串和散落的 Key 前缀。常量按共享范围和语义分组，避免维护一个无边界的全局常量类。
2. 只有一个值域且附带名称、排序或转换规则时使用枚举；枚举成员必须有明确含义，未知值的兼容策略要写入契约。
3. 构造器只建立对象不变量，不执行远程调用、写库、启动线程或依赖外部可变状态。需要显式初始化时使用命名方法或工厂，并说明失败语义。
4. 成员和方法采用最小可见性。仅供类内使用的内容使用 `private`；工具类禁止暴露无意义的公共构造器；静态成员只有在确有共享语义时才使用。
5. DTO、Entity 和配置对象不要通过隐式默认值掩盖缺失输入。默认值必须在契约边界显式产生，并能区分“未提供”和“提供了零值”。

## 4. SQL 与数据库迁移

### 4.1 SQL 规则

1. 所有数据值使用参数绑定，禁止拼接用户输入。动态排序和列名使用服务端白名单映射，禁止外部字符串进入原样替换语法。
2. 查询显式列出字段，应用持久化查询不得使用 `SELECT *`；诊断探索查询不属于此限制。
3. 查询受保护数据时必须包含授权范围条件；分页在数据库完成，并使用稳定排序和明确的第二排序键。
4. UPDATE/DELETE 必须限定目标、归属和必要的旧状态，检查影响行数，限制批量规模。
5. 业务不变量优先用唯一约束表达；应用层前置查询不能单独保证并发唯一性。
6. 索引依据真实的过滤、排序、连接和唯一约束设计，并通过执行计划验证。
7. Entity、Mapper、SQL、DTO 和 DDL 的字段、类型、枚举值、时间精度和可空性必须保持一致。

8. 聚合统计必须明确 NULL 语义；`count(*)`、`count(column)` 和 `sum` 的选择要与业务含义一致。分页在确认总数为零时不得继续执行无意义的数据查询。
9. 跨服务一致性不能依赖数据库外键。单库内可以使用外键保障引用完整性；级联、触发器和存储过程必须评估锁、隐式副作用、迁移及可测试性，不作统一禁用。
10. 数据订正先以只读查询确认目标范围，再执行受限更新或删除；脚本必须输出影响行数并提供恢复依据。批量 `IN`、深分页、模糊搜索和多表连接必须以真实执行计划和数据规模为依据。
11. 金额、计量和比例等需要精确计算的值使用定点或整数方案；不得因类型默认行为引入浮点精度损失。

### 4.2 表、索引与 ORM 约定

项目必须在附录中确定数据库命名、主键、审计字段、逻辑删除、字符集、索引前缀和时间精度。通用手册只提出以下原则：

- 表名和字段名使用统一的小写命名规则，避免保留字、复数歧义和无语义缩写；索引名称能够表达类型和字段；数据库固定的主键索引名不强制改名。
- 业务唯一性由数据库唯一约束兜底，应用层校验只负责提供更友好的错误。
- 索引服务于真实的过滤、排序、连接和唯一约束；新增索引必须有执行计划或基准证据，删除索引必须有使用情况证据。
- ORM 查询必须显式声明结果字段和映射关系；查询结果使用明确类型，不用无约束的 `Map` 或 `Object` 逃避模型设计。约定映射、注解和 XML 均可使用，不强制所有查询编写 resultMap。
- 更新只写入确实变化的字段，并同步维护约定的修改时间；动态 SQL 的列名和排序字段只能来自白名单。

### 4.3 迁移脚本

迁移脚本使用唯一、可排序的版本号和描述，例如 `V<YYYYMMDD>_<序号>__<change_description>.sql`。已经在共享环境执行的脚本不得原地改写，修正通过新版本完成。

每次迁移必须检查目标库版本、已有迁移、数据分布、锁和耗时、索引影响、备份或恢复来源。必须在隔离的真实数据库中试运行，并记录版本、校验和、执行结果、失败位置和恢复步骤。

空库初始化和旧库升级后的结构必须一致，包括表、列、索引、约束和默认值。`IF NOT EXISTS` 不等于结构一致；数据库 DDL 的回滚能力不能由应用层事务注解推断。破坏性 DML 必须提供受影响记录清单和可恢复的原值或前向修复方案。

## 5. 测试与验收

### 5.1 测试层级

| 层级 | 能证明什么 | 不能代替什么 |
|---|---|---|
| 单元测试 | 业务分支、规则、错误转换和恢复决策 | 真实 SQL、事务和缓存原子性 |
| HTTP 契约测试 | 状态码、响应字段、参数校验和认证错误 | 完整部署拓扑和物理数据一致性 |
| 数据库集成测试 | 真实 Mapper、索引、事务、JSON、时间和并发更新 | 缓存、界面和供应商行为 |
| 缓存集成测试 | Key、TTL、撤销、原子操作和并发行为 | 数据库回滚和界面状态 |
| 端到端测试 | 用户交互、网络、服务、数据库和缓存的共同状态 | 未被场景覆盖的不变量 |

### 5.2 测试代码

- 使用 Arrange、Act、Assert；一个测试表达一个业务结果。
- 使用固定时间和确定性夹具；不要依赖当前日期、随机顺序或固定睡眠。
- 只 Mock 外部边界和无关依赖，不 Mock 正在验证的 SQL 或核心算法。
- 失败路径要检查没有错误写入、事件或重复副作用，而不只断言异常类型。
- 测试结束清理数据库隔离数据、缓存、MDC、线程上下文和静态状态。
- 一个场景需要大量 Mock 时，先检查生产类是否承担了过多职责，不要只把 Mock 隐藏到测试基类。

### 5.3 真实数据库测试矩阵

至少覆盖用户隔离、分页边界、唯一约束并发、旧状态更新、事务回滚、统计 SQL、JSON 和时间往返、缓存 TTL、事件重复消费以及迁移升级一致性。并发测试使用屏障、锁存器或等价同步机制，不能用连续调用冒充并发。

测试使用专用数据库和缓存命名空间，只清理本轮数据，禁止对共享环境执行全量清空。端到端验收必须同时检查界面或 HTTP 结果、数据库物理行、缓存生命周期、服务日志和测试后环境清理。

### 5.4 单元测试准入

单元测试必须自动执行、相互独立、可重复运行，并通过断言而非人工观察判定结果。测试数据通过受测程序或合法夹具准备，不依赖开发者手工修改数据库。核心规则至少覆盖正确输入、边界输入、非法输入和异常恢复；覆盖率指标由项目附录按风险确定，不以单一百分比替代测试设计。

## 6. 存储、AI 与诊断

### 6.1 对象存储

业务模块负责对象的业务状态，存储 Client 负责供应商协议。签名生成、上传完成和数据库登记是不同状态，不能互相替代。对象 Key 与访问 URL 分开管理，校验归属、类型、大小和过期时间。数据库与对象存储不是一个本地事务，删除、重试和孤儿对象补偿必须有明确策略。

### 6.2 AI 客户端

Client 负责模型协议、超时、重试和结构解析；Service 负责业务时序以及是否接受模型输出。输出落库或展示前必须校验结构、长度、枚举和事实依据。记录模型标识、提示词版本、耗时和结果；未知用量保持未知。模型、提示词、图片和工具结果都是不可信输入，不能直接驱动 SQL、类加载或未授权副作用。

### 6.3 诊断与性能

请求、数据库动作、异步任务和外部调用使用可关联的诊断标识。日志只记录排障所需的最小字段。性能结论必须说明环境、数据量、采样方式和分位数；不得在注释中承诺未经测量的延迟或可靠性。普通遥测故障不应改变业务结果；强制审计写入失败是否阻断操作必须由审计契约规定。

## 7. 安全与工程依赖

### 7.1 安全边界

1. 必须在服务端校验认证身份和资源权限；参数绑定只能防止 SQL 注入，不能替代授权。[S6]
2. 输入必须有长度、数量、取值范围和格式边界。分页、批量请求、文件解压和正则匹配必须限制资源消耗；不得通过不可信输入选择反序列化类型或加载任意类。
3. 返回数据应按用途最小化并脱敏。HTML、属性、URL 和 JavaScript 输出使用对应上下文编码；允许富文本时使用维护中的 HTML 清洗器，不能用正则替代清洗。[S8]
4. 使用浏览器自动附带的凭证进行状态变更时，必须采取框架 CSRF 防护、令牌或来源验证等适用措施。SameSite 是纵深措施，不默认视为完整替代；GET 不应修改业务状态。[S7]
5. 重定向和服务端访问的外部 URL 必须校验协议及目标范围；涉及服务端抓取时还应防范内网访问、重定向绕过和 DNS 变化。
6. 短信、邮件、上传、下单及模型调用必须限制频率、并发和成本；高价值操作需防重放。限流不能替代业务幂等。
7. 日志、异常响应、toString 和测试快照不得泄漏密钥或凭证；密钥通过受控配置注入，不写进源码和示例。

### 7.2 依赖与构建

1. 发布物必须能够追溯到源码版本、JDK、构建工具和依赖版本。正式发布不依赖可变 SNAPSHOT；已发布的版本不得覆盖替换。
2. Maven 项目应通过 dependencyManagement 或 BOM 集中管理依赖版本；管理版本不等于引入依赖，子模块按实际用途声明 dependencies。[S3]
3. 升级依赖必须检查依赖树、版本仲裁、API 兼容性和安全公告。Maven 的最近路径仲裁不是业务兼容性保证，禁止依赖偶然的声明顺序解决冲突。[S3]
4. 二方库应只暴露稳定契约，不强制携带日志实现或不必要框架。库中测试、运行和可选依赖应使用正确 scope。
5. 版本号应按已发布的兼容策略演进；不兼容变更提供迁移说明，弃用 API 说明替代方案及移除条件。
6. 单元测试、静态检查和格式检查必须进入构建流程；集成测试单独标识其环境依赖，不允许因跳过而显示成通过。
7. JVM 堆、容器内存、线程、连接池、文件描述符和转储策略应按实际容量配置。不得直接复制固定堆大小、内核参数或历史网络调优值；堆转储可能含敏感数据，必须控制访问和保留期。

## 8. 评审清单

- 类的职责、边界、命名和依赖是否一眼可见？
- Controller 是否只做协议承接，Service 是否保持连续的业务流程？
- 跨模块调用是否经过最小契约，数据表是否有唯一写入所有者？
- 查询是否参数化、隔离、分页稳定，更新是否检查影响行数？
- 事务、异步、重试和幂等边界是否有明确语义？
- 异常、日志和敏感数据处理是否符合统一安全要求？
- 测试是否验证了真实 SQL、事务、缓存和并发，而不是只验证 Mock？
- 迁移是否可追踪、可试运行、可恢复，升级后结构是否与空库一致？
- 存储、AI 和诊断失败是否不会伪造成功或改变业务结果？

## 10. 通用代码示例

以下 Java 正例以 Java 17 为编译基线，仅依赖 JDK。每个示例是独立源文件；包声明省略。Java 21 虚拟线程规则见 3.11，不由这些示例验证。

### 10.1 对象不变量与空值

正例：构造器建立局部不变量，集合做防御性复制；record 只提供浅层不可变性，元素自身仍需满足契约。

```java
import java.util.List;
import java.util.Objects;

/** 已校验的标签集合；不接受空元素。 */
public record LabelSet(List<String> labels) {
    public LabelSet {
        labels = List.copyOf(Objects.requireNonNull(labels, "labels"));
    }

    /** 返回是否包含指定标签；null 输入返回 false。 */
    public boolean contains(String label) {
        return label != null && labels.contains(label);
    }
}
```

反例（行为说明）：直接保存调用方的可变 List，随后调用方修改集合，会改变 record 内部可见状态。不能仅凭 record 声明认定深度不可变。

### 10.2 包装类型、集合与比较器

正例：明确值相等、复制范围视图、原地删除及排序契约。[S1]

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.Objects;

/** 演示集合边界；不修改调用方输入。 */
public final class CollectionRules {
    private CollectionRules() {}

    /** 比较可空标识的值，两个 null 视为相等。 */
    public static boolean sameId(Long left, Long right) {
        return Objects.equals(left, right);
    }

    /** 复制并筛选前 limit 项；越界抛 IllegalArgumentException。 */
    public static List<String> sortedPrefix(List<String> source, int limit) {
        Objects.requireNonNull(source, "source");
        if (limit < 0 || limit > source.size()) {
            throw new IllegalArgumentException("limit out of range");
        }
        List<String> result = new ArrayList<>(source.subList(0, limit));
        result.removeIf(Objects::isNull);
        result.sort(Comparator.comparingInt(String::length)
                .thenComparing(Comparator.naturalOrder()));
        return List.copyOf(result);
    }
}
```

反例（行为说明）：`left == right` 对包装类型比较引用；把 subList 强转为 ArrayList 依赖具体实现；比较器只返回 1 或 -1 会破坏相等值的契约。`Arrays.asList` 是固定大小视图，允许 set，但不支持增删；`List.of` 不允许修改或 null 元素。

### 10.3 查询绑定与资源关闭

正例：SQL 结构固定，授权范围作为查询条件，JDBC 资源按创建逆序关闭；连接由调用方管理。表名为教学示例，不指定某个项目 DDL。[S6]

```java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.Optional;

/** 按授权范围读取资源标题。 */
public final class ResourceQueries {
    private ResourceQueries() {}

    /** 无匹配返回空；数据库错误向上传播；调用方提供可信身份。 */
    public static Optional<String> findTitle(
            Connection connection, long resourceId, long ownerId)
            throws SQLException {
        String sql = "SELECT title FROM resource WHERE id = ? AND owner_id = ?";
        try (PreparedStatement statement = connection.prepareStatement(sql)) {
            statement.setLong(1, resourceId);
            statement.setLong(2, ownerId);
            try (ResultSet rows = statement.executeQuery()) {
                return rows.next() ? Optional.of(rows.getString("title"))
                        : Optional.empty();
            }
        }
    }
}
```

本例假设 title 为 NOT NULL。可空列应使用能区分“行不存在”和“列为空”的结果类型。反例（行为说明）：先拼接用户输入再 prepareStatement 并不能防止注入；排序列不能当作普通值绑定，必须白名单选择。

### 10.4 条件更新与并发控制

以下 SQL 是参数绑定示意，冒号参数需由实际持久化框架处理，并非可直接执行的迁移脚本。

```sql
UPDATE resource
SET status = :newStatus, version = version + 1
WHERE id = :id
  AND owner_id = :ownerId
  AND status = :expectedStatus
  AND version = :expectedVersion;
```

必须检查影响行数：一行表示完成本次转换；零行表示条件未成立，不能一律返回成功。错误响应不得为了区分原因泄漏未授权资源的存在性。重试应重读并重新计算，不可把相同旧版本无限重放。

### 10.5 方法编排与注释

以下为流程伪代码，不是可编译 Java。辅助方法命名描述业务步骤，不使用 step1、process2；本地事务由实际框架建立，不能从代码排版推断。

```text
updateResource(command, authenticatedActor):
    validateCommand(command)
    resource = loadAuthorizedResource(command.id, authenticatedActor)
    validateTransition(resource.status, command.targetStatus)
    changed = computeChanges(resource, command)
    persistWithExpectedVersion(changed, resource.version)
    appendOutboxEvent(changed)
```

前提：数据更新与 outbox 记录在同一数据库事务中；异步发布器提交后投递并可恢复重试；消费者处理重复事件。仅在提交后调用一次进程内回调不能提供同等投递保证。
